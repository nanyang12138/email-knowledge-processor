# 个人知识系统产品计划

状态：规划草案 v0.1  
日期：2026-08-16  
项目：Email Knowledge Processor

## 1. 已确认的产品目标

本项目不是一次性脚本，也不是用于演示的 MVP。目标是构建并公开发布一个：

- 能长期处理个人多年私人数据的完整知识系统。
- 能从邮件、附件和后续扩展的数据源中提取可信事实、案例、经验与规则。
- 能让 AI Agent 在处理新问题时检索、比较并引用用户过去的经验。
- 能持续吸收用户修订、任务结果和偏好，而不是生成一次后静态不变。
- 能在所有结论上保留来源、版本、时间、冲突和置信依据。
- 能面向其他用户部署，具备迁移、升级、备份、安全和可观测能力。
- 质量优先；模型调用成本不作为排除数据或降低分析深度的设计约束。

### 1.1 不可妥协原则

1. 所有数据都进入完整处理流程，不能因为成本而跳过低分邮件。
2. “低价值”只影响检索排序，不影响原始数据保存和未来重新分析。
3. 原始数据不可修改；所有清洗、聚合和知识均为可重建的派生层。
4. 任何正式知识都必须能够回到原始证据。
5. 引用存在不等于结论正确，必须区分字符串校验、语义蕴含和事实真实性。
6. 模型自报置信度不能单独作为质量依据。
7. 不将单一模型、单一供应商或 Cursor SDK 作为公开产品的唯一推理后端。
8. 不将“没有发现错误”宣传为“100% 准确”。
9. 公开仓库、测试数据和日志中不得包含私人或公司邮件。
10. 产品应优先支持本地优先或用户自托管，用户明确控制数据发送给哪个模型。

## 2. 产品定义

### 2.1 产品不是普通邮件搜索

普通邮件搜索解决“哪封邮件提到了某个关键词”。本产品需要解决：

- 我过去遇到过哪些相似问题？
- 当时有哪些约束、尝试、决定和结果？
- 哪些做法后来证明有效或无效？
- 这次情况与过去有什么相同和不同？
- 哪条旧经验已经失效或被新经验替代？
- 某个项目、人物、Issue、CL 或技术主题在多年中如何演变？
- Agent 应采用哪条经过证据支持的操作规则？

### 2.2 目标记忆类型

系统必须显式区分以下记忆，而不是把所有内容混成向量：

- 原始记忆：邮件、附件、元数据和不可变来源。
- 情景记忆：一次具体事件、线程、问题和处理过程。
- 语义记忆：人物、项目、系统、术语和相对稳定的事实。
- 程序记忆：可复用的流程、排查顺序、决策规则和操作手册。
- 偏好记忆：用户对工具、沟通方式、风险和决策风格的偏好。
- 关系记忆：人物、团队、项目和组织之间的关系及其变化。
- 时间记忆：事实何时成立、何时被替代、何时得到结果验证。
- 反馈记忆：用户对 Agent 建议的采纳、否定、修订及最终结果。

## 3. 当前代码评估

### 3.1 可以保留的设计

现有代码已经验证了若干正确方向：

- 原始 `body` 和完整记录与 `clean_body` 分离。
- RawJSON 优先于 CSV，避免浏览格式覆盖更完整来源。
- 文件哈希、消息去重、线程指纹和重复导入跳过。
- 按 `conversation_id` 组织线程。
- 提取与复核分离。
- 每条 claim 保存 `message_id` 和证据引用。
- 本地程序检查证据引用是否存在于来源正文。
- 区分 `verified`、`verified_with_gaps`、`partial` 和 `rejected`。
- 邮件正文被当作不可信输入，Agent 工具被禁用。
- SQLite 外键、完整性检查和自动测试已经建立。
- 候选线程开始考虑邮箱主人参与度和线程深度。

这些能力应迁移到正式架构，不能丢失。

### 3.2 当前代码不能直接承担正式产品的部分

以下部分需要重构或替换：

- SQLite 同时承担原始档案、业务状态、知识和报告，不适合未来多用户与服务化。
- 分析器一次把候选线程载入内存，不能无界处理多年数据。
- 线程划分过度依赖 Graph `conversation_id`，无法连接跨线程的同一事项。
- 只做精确重复正文削减，没有成熟的引用、签名、免责声明和 MIME 处理。
- 没有附件下载、内容解析、OCR、恶意文件检查和附件版本管理。
- knowledge 主要存为 JSON blob，不利于查询、版本、冲突和迁移。
- “经验”仍由单个线程直接生成，没有跨案例归纳和规则验证。
- 没有实体消歧、别名、项目归属、Issue/CL/构建标识符解析。
- 没有事实有效期、替代关系、冲突关系和撤销机制。
- 没有全文、向量、稀疏和图检索的统一召回与重排。
- 没有面向 Agent 的稳定 API、MCP Server 和权限边界。
- 没有提示词、模型、ontology 和数据版本的完整可重复记录。
- Cursor SDK 是唯一规划中的推理通道，不适合作为公开产品唯一后端。
- 没有正式数据库迁移工具、任务队列、分布式锁和长期运行恢复。
- 当前质量报告只能证明引用存在，不能证明语义蕴含、完整性和个人有用性。
- 没有用户反馈闭环、隐式反馈、推荐采纳和结果回写。
- 没有多用户隔离、ACL、加密、备份恢复、数据删除和合规流程。
- 没有产品 UI、安装器、自动更新和公开发布所需的文档体系。

### 3.3 当前试验说明了什么

首批 5 个线程经过两次独立分析和第三次复核：

- 27 条最终 claim 的证据引用全部通过本地存在性校验。
- 两次分析的分类一致，但重要度平均相差约 11.6 分。
- 两次分析分别生成 36 和 27 条 claim，说明知识粒度仍不稳定。
- 5 个线程全部缺少某种后续结果或上下文。
- 3 个相似自动审计线程本质上应归纳为一条通用处理规则，而不是三个并列知识卡。

因此，现有证据链设计有效，但重要度标定、知识粒度和跨案例归纳尚未完成。

## 4. 目标系统总体架构

```text
数据连接器
  ↓
不可变原始档案与内容寻址
  ↓
标准化、线程重建、附件解析
  ↓
消息级事件与证据抽取
  ↓
线程级案例与时间线
  ↓
跨线程事项、项目与实体关联
  ↓
跨案例模式归纳
  ↓
事实 / 经验 / 规则 / 偏好 / 关系 / 时间图谱
  ↓
全文 + 稀疏 + 向量 + 图 + 时间混合检索
  ↓
证据重排与上下文组装
  ↓
Agent API / MCP / UI
  ↓
用户反馈、任务结果、知识修订与版本演进
```

### 4.1 数据连接器层

第一阶段完整支持 Microsoft 365，后续通过统一连接器接口扩展：

- Microsoft Graph 邮件、文件夹、附件和增量同步。
- Outlook EML/MSG/PST。
- MBOX 和 Maildir。
- Gmail API。
- 本地文件目录。
- OneDrive、SharePoint 和常见文档格式。
- 可选的日历、Teams、任务和笔记来源。

每个连接器必须实现：

- 初次全量导入。
- 增量游标或 delta token。
- 删除和移动检测。
- 重试、限流、断点恢复。
- 权限和来源身份。
- 内容哈希与重复检测。
- 连接器版本和导入审计。

### 4.2 不可变原始档案

原始层使用内容寻址，不依赖某个 CSV 文件长期存在：

- 原始消息、附件和 API 响应以 SHA-256 标识。
- 原始对象只写不改。
- 保存来源、租户、邮箱、文件夹、抓取时间和连接器版本。
- 保存 Graph ID、internetMessageId、conversationId 等所有原始标识。
- 每次规范化结果都引用原始对象哈希。
- 支持重新运行任意新版解析器而不重新抓取数据。

推荐存储：

- 单机：受保护的本地对象目录。
- 自托管服务：S3 兼容对象存储，例如 MinIO。
- 元数据：正式关系数据库。

### 4.3 标准化与线程重建

不能只依赖 `conversation_id`。线程重建应综合：

- Graph conversationId。
- Message-ID、In-Reply-To 和 References。
- 标准化主题。
- 发送时间窗口。
- 参与者集合。
- 引用正文相似性。
- 转发和拆分线程识别。

输出：

- 标准消息。
- 消息之间的 reply/forward/references 边。
- 线程及线程置信度。
- 无法确定的候选关系，而不是强行合并。

### 4.4 正文与附件处理

每份内容至少保留三种表示：

- `raw_content`：原始内容。
- `canonical_content`：结构保真的规范化内容。
- `analysis_content`：供模型使用的去重表示。

清洗必须可解释和可回滚：

- MIME 解码和字符集处理。
- HTML 到结构化 Markdown，而非简单删除标签。
- 引用历史识别。
- 签名和免责声明分离。
- 追踪像素、CID 和无意义布局处理。
- 表格、代码、链接和列表保留。
- 语言检测。

附件流水线：

- 类型识别和哈希去重。
- Office、PDF、图片、压缩包、文本和邮件附件解析。
- OCR。
- 表格与页面结构保留。
- 恶意文件和宏扫描。
- 密码保护或无法解析状态。
- 附件内容与所属消息证据链。

候选开源组件需单独评估：

- Unstructured。
- Apache Tika。
- Docling。
- Presidio。
- ClamAV。
- 专用 EML/MSG/MBOX/PST 解析库。

任何组件在采用前必须完成许可证、维护活跃度、准确率和 Windows 支持审计。

## 5. 正式知识模型

### 5.1 核心对象

正式数据库不应只保存一个 `verified_json`。至少需要以下一等实体：

- `source_object`：不可变来源对象。
- `message`：标准化消息。
- `message_revision`：规范化和清洗版本。
- `attachment`：附件及其解析结果。
- `thread`：线程。
- `thread_membership`：消息与线程的带置信关系。
- `entity`：人物、组织、项目、系统、产品和术语。
- `entity_alias`：邮箱、名称、缩写和历史别名。
- `identifier`：CL、Issue、Build、Ticket、Commit 等标识。
- `event`：带时间的动作或状态变化。
- `claim`：一个原子结论。
- `evidence_span`：证据的来源对象、字符偏移、页码或单元格。
- `decision`：决定、候选方案、理由和决策者。
- `outcome`：结果、指标、时间和证据。
- `case`：一次问题处理或事项。
- `experience`：从一个或多个案例归纳的经验。
- `rule`：可复用的“如果—那么—除非”规则。
- `preference`：用户偏好及其适用范围。
- `relationship`：实体之间的关系。
- `feedback`：用户修订、采纳、驳回和最终结果。
- `knowledge_version`：知识版本。
- `access_policy`：访问控制和敏感级别。

### 5.2 Claim 状态

Claim 不能只有一个模糊置信分数。建议状态：

- `proposed`：模型提出。
- `evidence_present`：证据片段确实存在。
- `entailed`：独立验证认为结论由证据支持。
- `corroborated`：被多个独立来源支持。
- `contested`：来源之间存在冲突。
- `incomplete`：结论有证据，但缺少必要上下文。
- `superseded`：被更新事实替代。
- `retracted`：后续证据表明错误。
- `expired`：只在过去时间区间成立。

### 5.3 置信度拆分

不使用单一 `confidence` 表示所有质量。至少拆分：

- 来源完整度。
- 解析可靠度。
- 线程归属置信度。
- 证据存在性。
- 语义蕴含置信度。
- 多来源一致性。
- 时间有效性。
- 实体消歧置信度。
- 个人相关性。
- 未来复用价值。

### 5.4 时间语义

每个事实和关系支持：

- `observed_at`：系统何时看到。
- `occurred_at`：事件何时发生。
- `valid_from` / `valid_to`：事实何时有效。
- `supersedes`：替代哪一条旧知识。
- `contradicts`：与哪一条知识冲突。
- `derived_at`：何时、由哪个模型和版本生成。

## 6. 知识生成生命周期

### 6.1 消息级抽取

从每封消息提取：

- 原子事实。
- 人物、项目和标识符。
- 动作、请求、承诺和截止时间。
- 决策候选。
- 明确结果。
- 情绪或立场只在证据充分时提取。

每条输出必须绑定证据偏移，不只保存可变字符串引用。

### 6.2 线程级案例

按时间顺序重建：

- 触发问题。
- 澄清过程。
- 目标与约束。
- 候选方案。
- 实际行动。
- 决策和理由。
- 结果与后续。
- 未解决问题。

### 6.3 跨线程事项关联

使用以下信号连接不同线程：

- CL、Issue、Build、Ticket、Commit 等明确标识。
- 项目和系统实体。
- 参与者。
- 时间邻近性。
- 语义相似性。
- 附件和链接。
- 后续邮件中的引用。

关联必须保存依据和置信度，不能静默合并。

### 6.4 跨案例模式归纳

重复案例不能无限生成重复知识卡。归纳流程：

1. 对案例按问题、行动和结果聚类。
2. 识别共同条件和不同条件。
3. 区分“同一规则的实例”和“表面相似但机制不同”。
4. 生成候选规则。
5. 用支持案例和反例验证。
6. 记录适用边界、失败条件和例外。
7. 新案例到来后增量更新，而不是覆盖历史。

例如，多封“缺失特性引用”邮件应形成：

- 一条通用审计处理规则。
- 多个具体 CL 实例。
- 每个实例的处置和结果状态。
- 尚未确认的实例不能被写成已经修复。

### 6.5 用户反馈和结果回写

系统应记录：

- 用户是否查看某条知识。
- 是否用于回答。
- 用户是否采纳建议。
- 用户如何修改建议。
- 最终任务结果。
- 用户标记的重要、不重要、过时或错误。

隐式反馈不能直接修改事实，只能影响排序；事实修订必须有明确来源或用户确认。

## 7. 检索架构

### 7.1 多路召回

每次查询根据意图组合：

- 精确标识符检索。
- BM25/全文检索。
- 多语言 dense embedding。
- sparse embedding。
- 元数据过滤。
- 时间过滤。
- 实体和图遍历。
- 相似案例检索。
- 程序规则检索。
- 用户偏好检索。

### 7.2 重排

候选结果经过：

- 精确匹配优先。
- 多语言 cross-encoder 或 ColBERT late-interaction 重排。
- 来源质量。
- 时间有效性。
- 个人相关性。
- 冲突和失效惩罚。
- 查询类型专用权重。

### 7.3 推荐技术方向

质量优先的服务端参考组合：

- PostgreSQL：标准化数据、知识、版本、权限和事务。
- 对象存储：原始消息和附件。
- Qdrant：dense、sparse、BM25、metadata 和多阶段重排候选。
- 时间知识图层：先做适配器和 ADR，再在 Graphiti、属性图或自研关系层中选择。
- Temporal：长任务、重试、恢复和幂等工作流。
- FastAPI：内部与外部 API。
- OpenTelemetry：统一追踪。

公开产品不能一开始绑定上述唯一实现。必须定义存储和检索接口，并提供：

- 单机本地配置。
- Docker Compose 自托管配置。
- 未来的多用户服务配置。

### 7.4 模型与推理后端

提供统一 provider adapter：

- Cursor SDK 可作为开发和高级 Agent 执行后端。
- Azure OpenAI、OpenAI、Anthropic 和其他合规云模型。
- OpenAI-compatible 自托管模型。
- Ollama、vLLM 或 llama.cpp 本地后端。

每次分析记录：

- provider。
- model ID 和版本。
- prompt/template 版本。
- ontology 版本。
- 输入来源哈希。
- 参数。
- 输出。
- token/耗时。
- 评估结果。

## 8. Agent 使用层

### 8.1 Agent 查询合同

Agent 不得直接把向量结果当事实。标准流程：

1. 识别当前任务和约束。
2. 检索相关规则、案例和偏好。
3. 检查时间有效性和冲突。
4. 回溯支持线程与原始证据。
5. 比较当前情况和历史情况的差异。
6. 输出建议、适用边界、来源和不确定性。
7. 任务完成后写回结果和用户反馈。

### 8.2 对外接口

产品需要：

- REST/streaming API。
- Python 和 TypeScript SDK。
- MCP Server。
- CLI。
- Web UI。
- 可选桌面应用。

Agent API 必须支持只读模式和受控写回模式，不能默认允许 Agent 修改正式知识。

## 9. 准确性与评估体系

### 9.1 评估维度

不能只测最终回答。分别评估：

- 导入完整性。
- 内容哈希一致性。
- MIME/HTML/附件解析。
- 线程归属。
- 引用和签名清洗。
- 实体识别与消歧。
- Claim precision 和 recall。
- 证据定位。
- 语义蕴含。
- 冲突识别。
- 时间有效性。
- 决策和结果提取。
- 跨线程关联。
- 案例聚类。
- 规则归纳。
- 重要度与个人相关性排序。
- 检索 recall、precision、MRR、NDCG。
- 回答 groundedness、完整性和可操作性。
- Agent 任务成功率。
- 用户采纳率和修订率。

### 9.2 评估数据集

建立三层数据集：

- 公开基准：公开邮件语料和可发布的合成数据。
- 专家标注集：覆盖多语言、长线程、附件、冲突、转发和复杂决策。
- 私人保留集：只在本地评估，不进入仓库或第三方观测平台。

测试集按失败类型分层，不能只做随机采样。

### 9.3 自动验证

- JSON Schema 和字段完整性。
- 来源 ID 存在。
- 证据偏移和哈希匹配。
- 时间顺序。
- 引用来源权限。
- 输出中未出现来源不存在的实体或标识符。
- 同一 claim 的多模型验证。
- 反事实和冲突检查。
- 每次 prompt、模型或 parser 变更后的回归测试。

### 9.4 LLM 评估

可评估的开源方向：

- Ragas。
- DeepEval。
- Promptfoo。
- Arize Phoenix。
- Langfuse。
- TruLens。

使用前必须确认许可证、私有部署、数据留存和与所选模型后端的兼容性。

LLM-as-judge 只作为一种信号：

- 评估模型和生产模型尽量不同。
- 重要结论需要确定性证据检查。
- 关键基准需要人工或专家 gold label。
- 评估结果需保存解释和版本。

### 9.5 发布质量门槛

以下为计划目标，最终数值需由基准测试校准：

- 原始导入：不得有静默丢失；所有失败必须可枚举和重试。
- 正式 claim：证据定位有效率必须为 100%。
- 高风险 claim：必须通过独立语义验证或用户确认。
- 数据迁移：升级前后来源对象数和哈希必须一致。
- 删除：用户请求删除后，原始、派生、索引、缓存和备份策略均可说明。
- 检索：核心测试集 Recall@20 目标不低于 95%。
- 高价值 claim 提取：在专家标注集上 precision 目标不低于 95%，recall 目标不低于 90%。
- 回答：关键测试集中不支持来源的事实声明率目标低于 1%。
- 恢复：任务中断后不得重复写入或丢失已确认结果。

不能在没有足够标注集和置信区间时对外宣称达到这些指标。

## 10. 安全、隐私与治理

### 10.1 数据保护

- 传输加密。
- 静态加密。
- OS 密钥库或专用 secrets manager。
- 数据库、对象、索引和备份统一权限。
- 敏感级别和来源 ACL。
- 多用户严格租户隔离。
- 最小权限连接器。
- 审计谁在何时检索了哪些来源。

### 10.2 模型发送控制

用户可按数据源和敏感级别配置：

- 仅本地模型。
- 允许指定云模型。
- 发送前脱敏。
- 禁止附件。
- 禁止特定文件夹或联系人。
- 只发送检索到的最小证据。

Presidio 可作为候选脱敏组件，但必须评估多语言误报和漏报。

### 10.3 提示注入与恶意内容

- 邮件和附件永远作为不可信数据。
- 抽取任务默认禁用外部工具。
- 内容和控制指令使用不同通道。
- URL 不自动打开。
- 附件进入隔离区并扫描。
- Agent 写回需要权限和审计。
- 对注入样本建立专门回归测试集。

### 10.4 用户数据权利

产品必须提供：

- 全量导出。
- 按来源、时间、实体和知识类型删除。
- 撤销某个连接器。
- 重建索引。
- 查看每条知识来源。
- 查看模型处理历史。
- 恢复备份。
- 销毁密钥后的不可恢复删除说明。

## 11. 公开发布要求

### 11.1 发布形态

推荐顺序：

1. Docker Compose 自托管版本。

所有依赖、模型、embedding、reranker 和测试数据必须进入 SBOM 和许可证清单。

### 11.3 工程发布基础

- 数据库迁移工具。
- 稳定配置格式。
- 版本兼容策略。
- Docker 镜像签名。
- SBOM。
- 依赖漏洞扫描。
- secret 扫描。
- 单元、集成、端到端和恢复测试。
- 多平台 CI。
- 发布说明和升级指南。
- 示例数据必须是公开或合成数据。
- 安全政策和漏洞报告流程。
- 隐私说明和遥测开关。
- 备份与恢复演练。

### 11.4 不可对外承诺

在没有正式证据前不能宣传：

各阶段以质量门通过为结束条件，不以“功能看起来能跑”为结束。

### 阶段 A：产品规范与架构决策

- 数据分类。
- ADR 模板。
- 许可证策略。

### 阶段 B：不可变数据平台

- 正式关系模型。
- 数据库迁移。
- 文件与消息哈希。
- 完整导入审计。

验收：

## 15. 风险清单

### 高风险

- 私人或公司数据被错误发送给未批准模型。
- 模型把通知要求误写成用户实际行动。
- 跨线程错误合并形成虚假经验。
- 重复自动通知污染知识和检索结果。
- 附件缺失导致错误完整性判断。
- 模型输出有证据片段，但结论并不由证据蕴含。
- 公开产品依赖许可证不兼容组件。
- 多用户部署发生权限越界。

### 中风险

- 中英文检索分词和 embedding 不一致。
- 历史事实没有失效时间。
- 模型升级导致知识漂移。
- 线程过长导致上下文遗漏。
- 用户反馈过少，个人相关性难以标定。
- 本地部署复杂度影响采用。

### 控制策略

- 数据策略先于模型调用。
- 所有派生知识可重建。
- 多阶段验证和冲突状态。
- 版本化模型、prompt、ontology 和 parser。
- 分层评估和回归门。
- 权限在检索前过滤。
- 公开合成测试集和私有保留测试集分离。

## 16. 完成定义

项目只有同时满足以下条件，才可称为“完整个人知识系统”：

- 多年数据可以完整、增量、可恢复地导入。
- 邮件和附件均有不可变来源。
- 线程和跨线程关联可解释。
- 知识以事实、案例、规则、偏好和时间关系存在。
- 重复案例能归纳，反例和例外可保存。
- 每条正式结论都有来源和状态。
- Agent 可检索经验并比较当前差异。
- 用户反馈和结果能够更新知识版本。
- 检索和回答质量有公开可重复的评估。
- 产品有安全、隐私、备份、迁移、删除和权限能力。
- 可在其他用户环境中安装、升级和恢复。
- 公开仓库不包含私人数据。
