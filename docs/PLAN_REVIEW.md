# 产品计划评审

状态：评审意见 v0.1  
日期：2026-08-16  
评审对象：[docs/PRODUCT_PLAN.md](PRODUCT_PLAN.md)（v0.1 规划草案）与当前 `src/email_kb` 实现

本文中的 `§` 一律指产品计划中的章节号，本文自身的章节直接写作「第 N 节」或 `N.M`。

## 0. 总体结论

计划的**知识建模方向是对的**，而且比市面上绝大多数"和你的邮件对话"类产品想得深。证据链、
时间语义、claim 状态机、记忆类型区分，这几件事一旦开始就很难回头补，计划在还没写代码之前
就把它们定下来了，这是这份计划最大的价值。

但计划有一个结构性问题：**它把最确定的事排在前面，把最不确定的事排在最后。**

阶段 B 到 F（对象存储、Postgres、附件解析、混合检索、工作流引擎）都是已经被工业界解决过的
问题，风险低、可预期。而整个项目真正的未知数只有一个：

> 从邮件里抽出来的东西，到底能不能让 AI Agent 把事情做得更好？

这个问题的答案在阶段 G 才会揭晓。如果答案是否定的，前面所有平台工作都白做。按现在的顺序，
你要先建完一整套生产级基础设施，才能第一次知道这个系统对你有没有用。

因此本评审的核心建议不是推翻计划，而是：**把阶段 G 的一个最小切片提到最前面，用它来决定
阶段 B 到 F 值不值得按现在的规模做。**

对"能不能当作个人知识库给 Agent 用"的直接回答见第 4 节。

## 1. 计划做对的部分

以下判断应当保留，不需要重新论证：

- **原始不可变 + 派生可重建**。这是唯一能让系统活过多次模型换代的结构。多年数据只抓一次，
  解析器和抽取器可以无限次重跑。
- **证据 span 而不是可变字符串引用**。当前代码存的是引文字符串，计划要求存来源对象加偏移，
  这个升级是必要的，因为正文一旦重新清洗，字符串引用就会失效。
- **claim 状态机取代单一置信度**。`proposed` / `entailed` / `contested` / `superseded` /
  `retracted` 的区分，是从"模型说了什么"走向"我们知道什么"的关键一步。
- **显式区分记忆类型**。情景、语义、程序、偏好、时间、反馈分开建模，而不是全塞进一个向量库。
  这一条直接决定了 Agent 能不能拿到"规则"而不只是"相关段落"。
- **§3.3 对首批实验的诚实记录**。两次分析产出 36 条和 27 条 claim、重要度相差 11.6 分、
  3 个相似线程应归纳为 1 条规则——这三条是整份文档里信息量最大的部分，它们准确地指出了
  真正的难点在知识粒度和跨案例归纳，而不在管道。
- **邮件视为不可信输入、工具禁用、注入回归集**。个人知识库天然是提示注入的高危场景，
  这个立场从第一天就正确。
- **不把 Cursor SDK 当唯一后端**。provider adapter 是对的，而且应该比计划里排得更早，
  因为它同时也是评估基础设施（同一批数据换模型跑，才能知道差异来自模型还是来自 prompt）。

## 2. 主要不足

按对项目成败的影响排序。

### 2.1 风险顺序倒置：最不确定的假设被安排在最后验证

§17 的执行顺序是：先做开源评估和 ADR，再做不可变层、附件、正式模型、跨案例归纳、混合检索，
最后才是 Agent API。§12 的阶段 G 排在第七位。

问题在于，这条路径上每一步的产出都无法独立验证"对我有没有用"。你会在完成一整套基础设施
之后，才第一次看到 Agent 拿着你的知识库干活是什么样子。而那时如果发现检索出来的"经验"
过于笼统、无法改变 Agent 的行为，你需要回退的不是一个模块，而是知识模型本身。

**建议**：在阶段 B 之前插入一个"薄切片验证"，用现有 SQLite、现有流水线、几百个线程，
搭一个最小的 MCP server，把 Agent 回路先跑通一次。目的不是交付产品，是拿到一个信号：
检索出来的知识是否真的改变了 Agent 的输出。这个信号会决定后面每一个阶段的投入规模。

### 2.2 验收标准只覆盖"正确"，没有覆盖"有用"

§9 的评估体系相当完整，但它衡量的几乎全是**忠实度**：证据定位有效率 100%、claim precision
95%、Recall@20 不低于 95%、无来源事实声明率低于 1%。

这些指标可以全部达标，而系统对你毫无价值。因为"张三在 2023 年 3 月 5 日回复说他会看一下"
是一条证据完备、定位精确、可被检索到的 claim，它同时也是一条废话。

§9.1 的列表里确实出现了"Agent 任务成功率"和"用户采纳率"，但它们混在二十个条目中间，
没有定义任务集、没有基线、没有对照组。而这恰恰是唯一直接对应产品目标的指标。README 自己
也承认了这个缺口：`evidence_pass_rate` 只表示引用存在。

**建议**：建立一个**决策回放集**作为第一等评估手段。

1. 从邮箱里挑 30 到 50 个你已经知道结局的真实问题。
2. 对每个问题，只提供事发时间点**之前**的数据。
3. 让 Agent 给出处置建议。
4. 对照实际发生的事情和最终结果打分。
5. 分别在"接入知识库"和"不接入知识库"两种条件下运行。

两者的差值，就是这个项目的全部价值。没有这个数字，其他所有指标都只是在证明系统没有说谎，
而不是在证明系统有用。这个数据集只有你本人能建，且应该在写更多代码之前就开始建。

### 2.3 "经验"缺少可操作定义，导致粒度不可能稳定

§3.3 已经观察到两次分析产出 36 条和 27 条 claim。计划把这归因于缺少"跨案例归纳"，并安排
在阶段 E 解决。

但粒度不稳定的根因不是缺少一个流水线阶段，而是**目标本身没有被定义**。"一条经验"到底
是什么，文档里只有类型枚举（`experience`、`rule`、`preference`），没有一个具体样例说明
什么叫写得好、什么叫写得差。在这种情况下，无论加多少轮复核、换多少个模型，输出粒度都会
继续漂移，因为模型没有可对齐的目标。

§6.4 举的那个例子（多封"缺失特性引用"邮件应形成一条通用规则加多个 CL 实例）其实非常好，
但整份文档里只有这一个例子，而且是文字描述，不是可以直接用于对齐和评估的样例。

**建议**：由你**手写** 10 到 20 张理想的经验卡，作为 ontology 的一部分提交进仓库。内容是
你希望 Agent 具备的、你自己真实拥有的经验，格式包含：适用情境、触发条件、动作、理由、
例外、失败条件、已知反例。写完之后，抽取任务就从"总结这个线程"变成了"从原始邮件中重建出
这些卡片"——一个有标准答案、可以打分的任务。

这件事的顺序很关键：**先有目标形态，再谈自动生成**。

### 2.4 邮件数据本身的天花板没有被正面处理

这是我认为计划里最被低估的风险。计划把"用户反馈过少"列为中风险，但没有列入一条更根本的：

> 邮件里通常记录的是结论的通知，不是决策的推理过程。

真实情况是：

- 为什么选方案 B，往往发生在会议、当面讨论、Teams、或者根本只在你脑子里。邮件里只有
  "我们决定用 B"。
- 结果经常不回到邮件。计划自己的实验已经发现 **5 个线程全部缺少某种后续结果**，这个比例
  很说明问题，而且它不会随着样本量增大而改善。
- 最有价值的经验往往是隐性的——你不会给别人写邮件说"这类问题我一般先查 X 再查 Y"，
  因为那是你的默认行为。

所以即使流水线做到完美，产出也可能主要是**事件流水**而不是**经验**。§16 的完成定义里
"知识以事实、案例、规则、偏好和时间关系存在"这一条，可能在数据层面就无法完全满足。

**建议**：把"主动补全"提升为一等功能，而不是等反馈自然产生。系统应该主动做两件事：

1. **识别缺口并提问**。当一个高价值案例缺少结果或缺少决策理由时，把它排进一个问询队列，
   每周问你三五个问题："这个事最后怎么样了？""当时为什么没选方案 A？"你的回答作为一等
   来源写入知识库，与邮件证据同级但标注为用户口述。这是把隐性经验转成显性知识唯一可行的
   路径，而且每个 token 的信息密度远高于重新处理六年的自动通知。
2. **把日历、Teams、文档从"可选"提到"重要"**。§4.1 把它们列为 optional，但决策理由和会议
   结论恰恰主要在那里。仅靠邮件，缺失结果的比例会长期居高不下。

### 2.5 检索层设计的是文档检索，不是案例检索

§7 是一套标准的 RAG 架构：BM25 加 dense 加 sparse 加重排。这套东西回答的是"哪些内容和
这段文字相关"。

但 Agent 实际发出的查询不是这个形状。Agent 的问题是：

> 我现在遇到情况 S，约束是 C，这个人过去在类似情况下怎么做的，结果如何？

这是**按情境相似度做案例检索**，不是按内容相似度做文档检索。两者的区别很实际：

- 两个案例可能用词完全不同（一个讲构建失败，一个讲测试超时），但机制相同（都是依赖版本
  漂移），正文 embedding 不会把它们拉近。
- 反过来，两封用词高度相似的自动审计通知，可能对应完全不同的处置，embedding 会把它们
  混为一谈。§6.4 已经识别出这个问题（"区分同一规则的实例和表面相似但机制不同"），但
  §7 的检索设计里没有任何对应机制。

更重要的是，**排序信号里缺了最关键的一个**：这条经验过去被采用后，结果是好是坏。§5.1 定义了
`outcome` 实体，但 §7.2 的重排因子里只有来源质量、时间有效性、个人相关性、冲突惩罚，
没有"历史成功率"。一条被验证过三次都有效的规则，和一条只出现过一次且结果未知的做法，
在当前设计里的排序权重是一样的。

**建议**：为 case 建立结构化的**情境指纹**（问题类型、涉及系统、触发条件、约束类别），
按结构化字段加语义混合匹配，而不是纯正文相似度。并把 outcome 状态作为重排的一等信号。

### 2.6 Agent 使用合同是约定，不是机制

§8.1 那七步流程写得很好，但它是一份**希望 Agent 自觉遵守的规范**。现实中 Agent 会调一次
检索，拿到结果，然后直接开始干活，不会主动执行第 3 步"检查时间有效性"和第 5 步"比较当前
情况和历史情况的差异"。

**建议**：把约束做进接口，而不是写进文档。

- 检索结果的返回结构**强制携带** `valid_to`、`superseded_by`、`applicability_conditions`、
  `counterexamples`。Agent 想忽略也得先看见。
- 当命中的规则处于 `contested`、`expired`、`superseded` 状态时，API 直接返回显式警告
  而不是把判断留给 Agent。
- MCP 工具按**任务意图**暴露，而不是按检索方式暴露。`search_knowledge(query)` 会被 Agent
  当成搜索框用；`find_similar_cases(situation)`、`get_applicable_rules(context)`、
  `check_if_i_tried_this_before(approach)` 才会引导出正确的使用姿势。

### 2.7 反馈闭环放得太晚

§6.5 的反馈设计是对的，但要到阶段 G 才实现。而当前最不稳定的两个量——重要度标定和个人
相关性——恰恰**只能靠反馈数据校准**。§3.3 里 11.6 分的重要度偏差不是 prompt 写得不好，
是模型根本不知道什么对你重要，而这个信息除了你本人没有任何来源。

标注数据是越早开始积累越好的资产，没有任何理由等到第七个阶段。

**建议**：现在就加一个最简单的形式，比如一条 `email-kb review` 命令，随机抽 20 条知识让你
标记"有用 / 没用 / 错了 / 过时了"。哪怕先只写进一张表、暂时不参与排序，也应该立刻开始积累。

### 2.8 技术栈与"本地优先、单人使用"目标存在张力

§7.3 推荐 PostgreSQL 加对象存储加 Qdrant 加 Graphiti 加 Temporal 加 FastAPI 加
OpenTelemetry。§11.1 又把 Docker Compose 自托管列为首选发布形态。

对一个主要服务于你自己的个人知识库来说，这套组合的运维负担会吃掉相当一部分精力，而且会在
你自己都还没用起来之前，先把项目变成一个运维项目。计划意识到要提供"单机本地配置"，但没有
说明单机版在不启动这六个服务的前提下如何提供同等能力。

**建议**：把 §7.3 改写为"能力接口加两档实现"，并且**默认档必须单进程可跑**。

- SQLite 加 FTS5 加 sqlite-vec 可以覆盖到几十万封邮件的规模，对个人数据量绰绰有余。
- Temporal 在单机档可以用一张持久化任务表加幂等键替代。当前代码里的 `idempotency_key` 和
  `input_sha256` 已经是这个思路的雏形。
- 图层在早期就是关系库里的一张 edges 表，不需要专门的图数据库。

服务档保留 Postgres 加 Qdrant 加 Temporal，但它应该是"当你决定给别人用时"的选项，不是
你自己每天要维护的东西。

### 2.9 "成本不作为约束"的隐藏代价是迭代速度

§1 的第 7 条目标和 §1.1 的前两条原则强调质量优先、不因成本跳过数据。作为**数据策略**这是
对的：不能因为省钱就丢掉原始数据。

但计划把它顺延成了**处理策略**，这会带来一个真实的问题。六年邮件乘以每线程两次调用，
再加上计划要求"模型或 prompt 更换可重跑和比较"，意味着每次改 prompt 都是一次全量重跑。
当一次全量重跑的周期变得很长，你就会开始不敢改 prompt——而改 prompt 恰恰是提升质量最
有效、最高频的手段。

**这不是钱的问题，是迭代速度的问题。**

**建议**：明确区分"不丢数据"和"对所有数据做同等深度的处理"，写成分层策略：

- **全量**：确定性的结构化处理（解析、线程重建、实体、标识符、时间）。这部分不需要大模型，
  应该对所有数据无差别执行。
- **候选高价值**：多模型深度抽取加交叉验证。
- **其余**：保留原文和索引，**在被检索命中时按需深度分析**。

这与原则 1 和 2 完全兼容——原则说的是不能因成本丢弃数据，不是必须一次性对所有数据做最贵的
处理。计划现在的措辞容易被执行成"必须先花巨量算力跑完六年才能开始用"，需要说清楚。

### 2.10 完成定义过于绝对

§16 列了 12 条，要求全部满足才能称为"完整个人知识系统"。这个门槛的实际效果是这个项目
永远不会被宣布完成，也就永远不会有一个可以停下来评估的里程碑。

**建议**：拆成"自用可用"、"可分享"、"可公开发布"三档。第一档应该很近，而且只需要其中
三四条。

## 3. 当前实现中已经违背计划原则的地方

以下都是代码层面可验证的具体问题，其中前三条会直接影响你对当前质量的判断。

### 3.1 "第二次独立复核"实际上不独立

`_verify_prompt`（`src/email_kb/analysis.py:363`）把第一次的完整结果放进 `<proposed_analysis>`
交给复核模型：

```text
<proposed_analysis>
{json.dumps(proposed, ensure_ascii=False)}
</proposed_analysis>
```

这是**锚定**，不是独立验证。复核模型看到了答案再去审，天然倾向于确认而不是反驳。
计划 §3.3 观察到的"两次分析的分类一致"很可能正是锚定的结果，而不是两次独立判断的一致。

要拿到真实的稳定性信号，需要**盲跑**：第二个模型在不看第一份结果的情况下独立抽取，然后
第三步做对账，把两份结果的差异本身作为不确定性的度量。计划 §3.3 的表述像是做过独立双跑，
但代码里的流程不是这样，两者需要对齐。

### 3.2 `verified` 状态由模型自报字段决定

`analyze_database`（`src/email_kb/analysis.py:751`）用复核模型自己返回的 `summary_grounded`
布尔值来决定能否标记为 `verified`：

```python
if corrected and not errors and bool(audit.get("summary_grounded")):
    status = (
        "verified_with_gaps"
        if bool(corrected.get("needs_more_context"))
        else "verified"
    )
```

同样，报告里的 `average_verifier_confidence` 来自模型自报的 `factual_confidence`。

这直接违反计划 §1.1 第 6 条："模型自报置信度不能单独作为质量依据。"目前 `verified` 这个
状态的含义比它看起来要软。

### 3.3 摘要是唯一完全没有程序校验的字段，却最可能被下游直接引用

`_validate_corrected_thread`（`src/email_kb/analysis.py:446`）对 `summary` 只检查了非空：

```python
summary = result.get("summary")
if not isinstance(summary, str) or not summary.strip():
    errors.append(f"{thread_id}: summary must be a non-empty string")
```

claim 有逐条引文校验，summary 没有。而 Agent 检索时最先看到、最可能直接采信的往往就是
summary。这是当前证据链上最大的一个缺口。

### 3.4 `evidence_pass_rate` 的统计口径会高估质量

`evidence_claims_checked` 统计的是**复核模型返回的** claim 数，被复核模型删掉的那些
（计划 §3.3 里 36 减到 27，共 9 条）根本不进分母。第一次抽取的输出完全没有经过程序校验
就被 `record_run` 存下来了。

所以 100% 的通过率含义是"复核后保留下来的 claim 全部有引文"，而不是"抽取模型不产生幻觉"。
真实的抽取幻觉率目前是未知的。建议对 extraction 阶段的输出也跑一遍同样的校验，只记录不
拦截，这样才能量化两个阶段各自的错误率。

### 3.5 引用去重几乎不会生效，长线程会被大量判为 oversized

`remove_exact_prior_content` 只删除**完全一致**的历史正文，并且要求匹配位置至少在 40 字符
之后、尾部残留不超过 80 字符。

真实的 Outlook 回复几乎总是会改写引用历史：加 `> ` 前缀、重新折行、HTML 转文本时空白处理
不同、中间插入 `From/Sent/To/Subject` 头。这些都会破坏精确匹配。结果是长线程的正文会随
轮次线性膨胀，很快撞上 `max_chars_per_batch` 默认的 80000 字符，被标记为 `oversized`。

而**最长的线程往往正是最有价值的线程**（多轮讨论、真实决策过程）。当前设计会系统性地把
它们排除在分析之外。不截断冒充完整的判断是对的，但需要一条降级路径：分段抽取加合并，
而不是整条丢弃。这件事的优先级应该高于计划里阶段 C 的位置。

### 3.6 其他

- **没有 schema 版本表**。`SCHEMA` 里全是 `CREATE TABLE IF NOT EXISTS`，没有任何版本标记。
  现在加一张 `schema_version` 表几乎零成本，等有了几万条分析结果再补会非常痛苦。
- **owner 匹配用 JSON 字符串子串搜索**。`iter_thread_ids` 里的
  `INSTR(LOWER(m.to_recipients_json), LOWER(?))` 无法走索引，而且会误匹配——如果你的地址
  是别人地址的子串就会命中错误的线程。规模上去以后这是全表扫描。
- **`analyze_database` 一次性把所有 document 载入内存**再分批，计划 §3.2 已经指出，
  这里只是确认它确实存在。
- **`partial` 状态的知识仍然写入库**。校验失败的线程保留了通过校验的 claim 并落库。
  这本身合理，但下游检索必须显式按 status 过滤，否则未完全验证的知识会混进 Agent 的
  上下文。这一点在计划的检索章节里没有写。
- **`evidence_in_text` 的最小长度对中文过短**。归一化后要求 8 个字符，中文没有空格，
  "我们决定采用方案B" 就已经达标。短引文加子串匹配容易巧合命中，也容易引用到真实存在
  但与结论无关的片段。计划的 `entailed` 状态是正确的解法，但在它落地之前，当前的证据
  校验提供的保证比看起来弱。

## 4. 关于"能不能作为个人知识库给 AI Agent 用"

直接回答：**能，但需要把它拆成两个难度差一个数量级的目标，分别看待。**

### 4.1 第一层：让 Agent 检索你的历史事实（可行，且价值立刻可见）

让 Agent 能回答"这个项目之前发生过什么""这个错误我以前遇到过吗""当时是谁负责的""那个
CL 最后怎么处理的"。

这一层用**现有架构和现有数据**就能达到，不需要等阶段 B 到 F。它的价值不依赖于"归纳出
经验"这件难事，只依赖于检索质量和证据链——而这两点当前代码已经具备雏形。

这一层应该尽快跑通，因为它同时也是验证第二层的实验平台。

### 4.2 第二层：让 Agent 具备你的经验（可行，但比计划预期的难，且受数据天花板限制）

"Agent 具备了我的经验"这个说法，实际需要成立三件事：

1. 经验存在于邮件里。——**部分成立**。见 2.4，推理过程和结果大量缺失。
2. 能被稳定地抽取成规则。——**尚未验证**。见 2.3，粒度目前不稳定，且缺少目标形态。
3. 能在正确的时机被检索到并改变 Agent 的行为。——**完全未验证**。见 2.5 和 2.6。

三件事任何一件不成立，这一层就打折。计划的阶段 E 方向正确，但我认为它会比文档预期的难
得多，而且**难点不在工程，在于你需要亲自参与归纳**。

更现实、也更值得追求的形态，不是"Agent 自动获得了你的经验"，而是：

> Agent 在动手之前会先问一句"这个人过去在类似情况下是怎么做的"，并且拿到一个带证据、
> 带适用边界、带反例、带历史结果的答案。

这个形态当前架构完全支持，而且它对第 2.4 节说的数据天花板容忍度高得多——即使只有一半
案例有明确结果，剩下一半作为"有先例但结果未知"返回，对 Agent 依然有价值。计划 §16 那
12 条完成定义给人的期待偏高，建议按这个形态重新描述产品承诺。

## 5. 建议的修订执行顺序

对 §17 的替换建议。核心变化是把风险验证提到最前面，平台化推后到有数据支撑之后。

### 第 0 步：定义"好"（只有你能做，且必须先做）

- 手写 10 到 20 张理想经验卡，进仓库作为 ontology 的一部分。
- 挑 30 到 50 个你已知结局的真实问题，建成决策回放集。
- 不写代码。这一步的产出是后面所有工作的评分标准。

### 第 1 步：修正当前流水线的三个可信度缺口，跑到 300 到 500 个线程

- 改为盲跑双抽取加第三步对账，取消锚定复核（3.1）。
- `verified` 状态不再由模型自报字段决定（3.2）。
- 对 extraction 阶段输出也做证据校验，只记录不拦截，量化两阶段各自的错误率（3.4）。
- 加 `schema_version` 表（3.6）。
- 目的不是产出知识库，是拿到**真实的错误分布**。五个线程的样本量不足以支撑任何架构决策。

### 第 2 步：最薄的 Agent 回路

- SQLite FTS5 加 sqlite-vec，不引入任何新服务。
- 一个 MCP server，按意图暴露三个工具（2.6）。
- 用第 0 步的回放集做 A/B：接知识库 vs 不接知识库。

**这一步的结果决定后面所有投资的方向。**

### 第 3 步：按 A/B 结果分流

- 如果 Agent 输出明显变好——说明知识模型有效，按原计划推进平台化，且此时你已经知道
  哪些能力真正影响结果，可以据此排优先级。
- 如果检索到的东西正确但没用——问题在**知识粒度**，回到第 0 步细化 ontology，不要碰
  存储引擎。
- 如果检索不到该检索到的东西——问题在**情境检索**（2.5），优先做 case 情境指纹，
  也不需要换数据库。

在拿到这个结果之前，Postgres、Qdrant、Temporal、Graphiti 的选型讨论都是过早优化。

### 第 4 步：主动补全回路

- 缺口问询队列，每周三五个问题（2.4）。
- `email-kb review` 反馈标注（2.7）。
- 这两个东西产生的数据，价值高于再处理十万封自动通知。

### 第 5 步及以后

原计划的阶段 B 到 F，但优先级由第 3 步的结论重排。附件解析和长线程分段抽取（3.5）
大概率会排在最前，因为它们直接决定有多少数据能进入分析。

### 关于公开发布

建议明确推迟到你自己**已经日常使用**这个系统之后。§11 的发布要求（SBOM、多平台 CI、
许可证审计、安全政策、备份演练）是一笔很大的固定成本，在产品形态还没被自己验证之前投入，
风险是给一个还会大改的东西建了一套不会大改的发布流水线。
